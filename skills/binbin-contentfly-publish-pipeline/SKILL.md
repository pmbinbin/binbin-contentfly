# 彬彬内容发布工作流

把一篇已经定稿的视频逐字稿，分步推进到“标题已确认、发布文案已确认、封面已生成”。这是编排型 Skill，只负责阶段控制、参数传递、用户确认和状态续接，不复制子 Skill 的公式库、文案规则或封面风格规则。

按顺序调用：

- `dbs-xhs-title`：生成封面标题和第一版文字标题。
- `binbin-contentfly-publish-copy`：生成发布文案，并把其中的发布标题作为备选文字标题。
- `binbin-contentfly-cover`：沿用已确认的封面标题，先生成封面提示词，确认后再生成图片。

## 统一术语

全流程只使用以下名称：

- **封面标题**：由“主标题”和“副标题”组成，用于封面画面。
- **文字标题**：Phase 1 由 `dbs-xhs-title` 生成并经用户确认的标题。
- **备选文字标题**：Phase 2 由 `binbin-contentfly-publish-copy` 随发布文案生成的标题。

不要使用“发布标题”“作品标题”“封面图文字标题”等其他叫法。最终同时保留文字标题和备选文字标题，不自动合并，也不让后者覆盖前者。

## 运行前依赖预检

每次启动新工作流时，从本 Skill 目录运行：

```bash
bash scripts/check-dependencies.sh
```

- 输出 `PUBLISH_PIPELINE_DEPENDENCIES_OK=1`：记录三个依赖路径并继续。
- 输出 `PUBLISH_PIPELINE_DEPENDENCIES_OK=0`：停止核心流程，说明缺少的 Skill。
- 不自动安装、不复制子 Skill，也不把子 Skill 的正文打包进本 Skill。
- `dbs-xhs-title` 缺失时，提供其上游 dbskill 来源和安装命令，但必须先取得用户同意才能安装。
- 同仓库的发布文案或封面 Skill 缺失时，提示用户重新安装完整的 `binbin-contentfly` 仓库。

## 输入与读取规则

1. 接受本地 Markdown 路径、Obsidian 链接或用户直接粘贴的完整逐字稿。
2. Obsidian 链接先解析 vault 和 URL 编码后的 `file` 参数，再定位本地文件。
3. 完整读取源内容，区分逐字稿、制作备注、品牌 brief 和历史方案；只把最终逐字稿当作内容真源。
4. 源内容不存在、为空或无法辨认正文时停止，不根据文件名猜内容。
5. 每个阶段开始前重新读取最新源文件；如果逐字稿已发生实质变化，提示已有标题或发布文案可能失效，再由用户决定是否重跑上游阶段。

## 商单类型硬规则

在第一次调用标题 Skill 之前，必须单独询问：

```text
这条视频属于哪一种？
1. 水上商单：封面标题和文字标题可以出现品牌名称
2. 水下商单 / 非商单：封面标题和文字标题不能出现品牌名称
```

- 即使 frontmatter 写了“商单”或逐字稿出现品牌名，也不得代替用户判断。
- 水上商单是“允许出现”，不是“必须出现”；仍根据标题效果决定。
- 水下商单/非商单时，封面主标题、封面副标题、文字标题和备选文字标题都不得出现品牌名、品牌简称或明显品牌变体。
- 这条限制默认只约束标题包装。发布正文可以按源稿真实提及产品或品牌；用户明确要求全文隐藏品牌时，再把限制扩展到正文和标签。
- 将用户选择传递给后续每个子 Skill，不在中途重新推断。

## 分步确认硬规则

1. 一次只执行当前阶段，不得因为用户最初说“完整发布”就连续跑完三个子 Skill。
2. 每个阶段完成后展示该阶段结果、当前状态和下一步，随后停止并等待用户明确确认。
3. 用户的最初请求不算对尚未展示结果的提前确认。
4. “确认”“可以”“下一步”“继续”等肯定回复只确认当前已展示阶段，不跨越后面的确认点。
5. 用户修改上游结果时，所有依赖该结果的下游确认立即失效：
   - 修改封面标题后，旧封面提示词和图片生成确认失效。
   - 修改文字标题不强制重做发布正文，但要更新两版文字标题的展示状态。
   - 实质修改逐字稿后，标题、发布文案和封面提示词都标记为待复核。
6. 用户只要求其中一部分时，在完成并确认该部分后停止，不强迫走完整流程。

## 标准执行流程

### Phase 0：读取输入并确认商单类型

1. 运行依赖预检。
2. 解析并完整读取逐字稿。
3. 记录平台、品牌、已有标题、已有发布文案、背景素材和用户指定输出位置。
4. 无论能否从文件推断，都按“商单类型硬规则”询问用户。
5. 收到选择后再进入 Phase 1。

本阶段不得生成标题、发布文案或封面提示词。

### Phase 1：生成封面标题和文字标题

1. 重新读取最新逐字稿。
2. 完整读取并调用预检定位到的 `dbs-xhs-title/SKILL.md`。
3. 把逐字稿的话题、行业/受众、商单类型和品牌限制传入标题 Skill。
4. 按 `dbs-xhs-title` 的规则完成公式匹配，保留公式编号、候选标题、原始爆款举例、推荐理由和 Top 3。
5. 基于 Top 3 整理成三组标题组合。每组必须包含：
   - 封面标题：主标题，可按视觉节奏分为 1–3 行；
   - 封面标题：副标题，一般为一行短补充；
   - 文字标题；
   - 主标题和文字标题对应的公式编号及一句话理由。
6. 封面副标题用于补充“教程、实测、案例、避坑”等内容属性，不机械固定为“保姆级教程”，也不要求单独匹配公式。
7. 文字标题遵守 `dbs-xhs-title` 的小红书标题长度与张力规则；封面标题优先服从移动端可读性和分行效果。
8. 水下商单/非商单时，输出前逐项复查三组标题，删除所有品牌露出。

按以下格式展示：

```markdown
## 标题方案 1

封面标题：

主标题：
不会代码
我做了个教师工作台！

副标题：
保姆级教程！

文字标题：
不会代码，我给老师做了个AI工作台

公式来源：#36
推荐理由：...
```

展示三组方案和 Top 1 建议后，单独询问：

```text
请确认采用哪组，或者告诉我需要怎么修改。确认后我再生成发布文案。
```

用户确认前不得调用 `binbin-contentfly-publish-copy`。

### Phase 2：生成发布文案和备选文字标题

1. 保存用户已确认的封面主标题、封面副标题和文字标题。
2. 重新读取最新逐字稿。
3. 完整读取并调用同仓库 `../binbin-contentfly-publish-copy/SKILL.md`，让它按自身完整流程生成标题、短正文和话题标签，包括依赖预检、风险处理、人味校准与最终复检。
4. 把商单类型和标题品牌限制一并传入：水下商单/非商单时，它生成的标题不得出现品牌名；正文仍按源稿处理，除非用户另有要求。
5. 不要求发布文案 Skill 沿用 Phase 1 的文字标题。把它生成的标题重新标记为“备选文字标题”。
6. 同时展示两版标题，不评判为新旧版本，也不自动替换：

```markdown
文字标题：
{Phase 1 已确认标题}

备选文字标题：
{发布文案 Skill 生成的标题}
```

7. 展示完整发布文案和实际保存路径；如果子 Skill 按其规则写回文件，保留该结果，不另建重复的发布文案文件。

展示后单独询问：

```text
请确认发布文案是否可以使用。两版文字标题都可以保留，也可以指定其中一版。确认后我再制作封面。
```

用户确认前不得调用 `binbin-contentfly-cover`。

### Phase 3：生成封面提示词

1. 重新读取最新逐字稿，并带入已确认的封面主标题和副标题。
2. 完整读取并调用同仓库 `../binbin-contentfly-cover/SKILL.md`。
3. 明确告诉封面 Skill：标题已经由上游确认，禁止重新起标题；只负责根据平台、风格、背景和人物素材完成视觉方案。
4. 传递商单类型。水下商单/非商单时，封面中的标题文字不得额外加入品牌名称。
5. 用户未指定平台或风格时，遵守封面 Skill 的默认风格规则；不要在本工作流复制三个风格文件的细则。
6. 完整遵守封面 Skill 的强制两段式流程：本阶段只展示所选风格、参考图1路径和完整最终提示词。
7. 展示提示词后，使用封面 Skill 规定的原句询问：

```text
是否按这个提示词生成图片？
```

本阶段不得调用图片生成工具。

### Phase 4：确认后生成封面

只有用户明确确认 Phase 3 已展示的提示词后，才继续调用 `binbin-contentfly-cover` 的图片生成阶段：

1. 使用同一条已确认提示词、同一张参考图1和同一份背景素材。
2. 不重新随机选择人像，不临时修改标题或风格。
3. 生成完成后展示图片，并报告绝对保存路径。
4. 用户提出修改时，严格回到封面 Skill 的“生成后的修改”流程：先展示整合后的新版提示词，再次等待确认，禁止直接编辑或生成。

## 状态记录与续接

输入为本地文件或 Obsidian 链接时，在源文件同级创建或更新：

`[源文件名]-发布工作流记录.md`

记录文件只保存工作流状态和已经展示的结果，不复制子 Skill 的完整规则。至少包含：

```markdown
# 彬彬内容发布工作流：{标题}

- 源文件：{绝对路径}
- 商单类型：待确认 / 水上商单 / 水下商单或非商单
- 当前阶段：Phase 0 / Phase 1 / Phase 2 / Phase 3 / 已完成
- 更新时间：YYYY-MM-DD HH:mm

## 已确认的封面标题

主标题：...
副标题：...

## 两版文字标题

- 文字标题：...
- 备选文字标题：...

## 发布文案

- 状态：待生成 / 待确认 / 已确认
- 文件：...

## 封面

- 风格：...
- 提示词：待生成 / 待确认 / 已确认
- 参考图1：...
- 图片：...
```

- 每次进入或完成一个阶段都更新状态；修改前重新读取最新记录，不覆盖用户新增的无关内容。
- 用户直接粘贴正文且没有本地源文件时，默认只在当前对话维护状态，不擅自创建文件。
- 用户说“继续发布工作流”时，优先读取记录文件，从第一个未确认阶段继续，不重复已经确认的步骤。

## 完成时交付

全部阶段完成后，简短交付：

- 封面主标题和副标题；
- 文字标题；
- 备选文字标题；
- 发布文案文件路径；
- 封面图片路径；
- 工作流记录路径；
- 商单类型和标题品牌检查结果。

不要在最终回复中重复粘贴子 Skill 的完整诊断过程。

## 失败处理

- 缺少逐字稿：停止并要求用户提供正文或有效路径。
- 缺少直接依赖：停止，不用通用能力假装调用过子 Skill。
- 子 Skill 自己的依赖检查失败：遵守该 Skill 的失败处理，不绕过检查。
- 用户没有确认当前阶段：停在当前阶段，不自动向后执行。
- 用户要求跳过某阶段：可以跳过，但记录“用户明确跳过”；封面标题未确认时不得直接制作封面。
- 封面生成失败：保留已确认提示词、参考图和当前状态，报告错误后停在 Phase 4，避免重跑前两步。

## 说话风格

- 每轮只交付当前阶段必要的信息。
- 先展示结果，再说明当前状态和下一步。
- 不把内部路由、依赖查找和完整风险报告混入对用户的成稿。
- 用户用中文时，用中文回复。
