# 彬彬发布文案

把长文章或逐字稿压缩成能直接发布的作品文案。固定使用内置的李一帆样本规则确定结构，先用 `binbin-contentfly-risk-check` 做最小风险修改，再用 `renwei-writing` 保留彬彬自己的位置、体验和说话手迹。

## 运行前检查

从本 Skill 目录运行：

```bash
bash scripts/check-dependencies.sh
```

- 输出 `PUBLISH_COPY_DEPENDENCIES_OK=1`：记录 `RISK_CHECK_SKILL_PATH` 和 `RENWEI_WRITING_PATH`，继续。
- 输出 `PUBLISH_COPY_DEPENDENCIES_OK=0`：停止核心流程，说明缺少的 Skill，不得假装完成风险检查或人味校准。
- 不自动安装第三方 Skill。`renwei-writing` 上游来源为 `https://github.com/orange2ai/renwei-writing`；`binbin-contentfly-risk-check` 应来自同一 `binbin-contentfly` 仓库。

## 固定执行顺序

严格按以下顺序执行，不把风险检查放在人味校准之后作为主要改稿步骤：

1. 读取源内容与固定参考。
2. 起草发布文案。
3. 调用 `binbin-contentfly-risk-check` 执行模式，做最小风险修改。
4. 调用 `renwei-writing`，把风险修改后变硬的表达重新写顺。
5. 调用 `binbin-contentfly-risk-check` 诊断模式做最终只读复检。
6. 复检通过后再写入最终文件。

最终复检如果发现人味校准新引入了明确风险，只修改命中的最小范围，再对改动句补一次 `renwei-writing`，最后重新复检。最多循环两轮；仍有待确认项时保留原意并向用户说明，不反复洗稿。

## 必读参考

每次运行都完整读取 `references/li-yifan-publish-pattern.md`。它保存两组“长逐字稿信息 → 短发布文案”的映射、固定结构和彬彬示范稿。

- 默认始终使用这套规则，不要求用户再次提供李一帆文件夹。
- 用户临时给了其他参考样本时，可以吸收其平台格式、长度或标签写法，但不得覆盖内置的核心压缩逻辑，除非用户明确说“这次换一种发布风格”。
- 不需要读取李一帆长逐字稿全文；内置映射已经保留发布文案真正需要的压缩关系。

## 读取源内容

1. 读取用户给出的文章、逐字稿、Markdown 路径、Obsidian 链接或粘贴正文。
2. Obsidian 链接先解析 vault 和 URL 编码后的 `file` 参数，再定位本地文件。
3. 完整读取源文件，区分正文、逐字稿、制作备注和优化记录，只把实际成稿或逐字稿作为内容真源。
4. 记录用户指定的平台、输出位置、长度、标签数量和删除要求。用户没指定平台时，写一版抖音与小红书均可使用的通用文案。
5. 源内容不存在、为空或无法辨认正文时停止，不根据文件名猜内容。

## 提炼与起草

先在内部提炼四项，不把分析过程写进成稿：

1. 观众最熟悉的具体痛点或开场场景。
2. 视频实际解决了什么问题。
3. 最值得预告的 2–4 个步骤、知识点或前后变化。
4. 作者亲自做过以后最具体的感受，或这条内容适合谁。

再按内置参考起草一版：

- 标题使用“具体痛点/疑问 + 解决方向或结果”，避免只有产品名和“保姆级教程”。
- 第一段直接接住视频的痛点、冲突或成品效果，不先介绍背景。
- 中段压缩教程价值，不复述整篇逐字稿，也不把功能名排成说明书。
- 结尾落在这套方法对观众有什么用，或自然邀请观众跟着做一遍。
- 优先保留源文章已有的第一人称体验、客户原话、真实数字和操作顺序。
- 源文章没有第一人称证据时，不虚构“我亲测”、客户反馈、耗时、收益或失败经历。
- 产品名、功能名、数字、效果和限制必须与源文章一致。
- 默认生成 4–5 个精准的纯文本标签；不伪造平台搜索链接。
- 不自动补“正式交付前仍需人工检查”等通用风险尾巴。只有用户明确要求或源文把它作为重要内容时才写。
- 默认只交付一版成稿，不附结构诊断或多个完整版，除非用户要求候选方案。

## 强制调用 binbin-contentfly-risk-check

初稿完成后必须先执行风险处理：

1. 完整读取预检找到的 `binbin-contentfly-risk-check/SKILL.md`。
2. 运行该 Skill 的 `scripts/check-dependencies.sh`。只有输出 `RISK_CHECK_DEPENDENCIES_OK=1` 才继续核心流程。
3. 按该 Skill 要求完整读取预检找到的 `dbs-content-risk-check/SKILL.md` 和 `references/video-risk-rules.md`。
4. 把本轮初稿作为“发布标题、正文和话题标签”，以执行模式调用风险检查。
5. 先做完整语义风险判断，再检查彬彬内部禁用表达、品牌禁忌、AI 内容声明和素材真实性。
6. 只执行有明确风险机制或内部规则依据的最小修改。不能看到“最、第一、课”等单字就机械删除，必须结合语义判断。
7. 保留真实经历、具体数据、强观点、有效 Hook 和口语毛边；不使用谐音、拆字或暗号绕审核。
8. 在工作记录中保留“原文、修改后、原因”，但默认不把完整风险报告混进发布文案正文。

`binbin-contentfly-risk-check` 或它的 `dbs-content-risk-check` 依赖缺失时，本 Skill 不算完成。只有用户明确允许降级，才能只用内置规范手动检查，并标注未完成完整语义风险检查。

## 再调用 renwei-writing

风险修改完成后必须：

1. 完整读取预检找到的 `renwei-writing/SKILL.md`。
2. 完整读取其直接要求的 `references/post-edit-checklist.md`。
3. 只校准风险处理后的发布文案，不改源文章和参考文件，也不直接还原已确认的风险表达。
4. 确认文案里有一个真实说话位置：作者刚做了什么、怕什么、发现了什么。只能使用源文章中有依据的内容。
5. 少动，删除总结报告腔、宣传腔、工整排比、假深刻的“不是 X 而是 Y”和没有代价的漂亮话。
6. 保留自然重复、语气词、长短不一的呼吸和作者原来的用词，不主动制造金句。
7. 重点检查风险替换过的句子是否变成生硬的安全话术，再对照事后检查清单，只扫描本轮改动过的句子。
8. 交付时简短说明关键改动及原因，把否决权留给用户。

`renwei-writing` 缺失时，本 Skill 不算完成。只有用户明确允许降级，才能手动按上述原则处理，并标注“未实际调用 renwei-writing”。

## 最终风险复检

人味校准后，再以诊断模式调用一次 `binbin-contentfly-risk-check`：

- 重新读取最终文案，不检查对话里的旧版本。
- 只复检发布标题、正文和标签；没有图片、主页、评论区或实际音画时，如实记录边界。
- 没有发现需要优先处理的问题时，结束流程。
- 发现新风险时，按“最小风险修改 → 只对改动句做人味校准 → 再复检”处理，最多两轮。
- 最终复检是验收，不得借机扩写正文、削弱 Hook 或加入通用风险尾巴。

## 输出格式

默认格式：

```markdown
# 发布文案

发布标题

正文第一段。

正文第二段。

#标签1 #标签2 #标签3 #标签4
```

跟随内置样本使用短段落，不加粗关键词，不在成稿中展示“痛点、价值、CTA”等幕后标签。

## 写回规则

1. 用户指定输出路径时写到该路径。
2. 源文件同级已有唯一一个名称含“发布文案”的文件时，重新读取并更新它。
3. 没有现成文件时，默认保存为源文件同级的 `[源文件名]-发布文案.md`。
4. 同级存在多个可能目标时不覆盖，向用户确认具体文件。
5. 用户只要求在对话中给文案，或明确说不写文件时，不落盘。
6. 只有风险处理、人味校准和最终复检完成后才写入文件。
7. 修改已有文件前重新读取最新内容，保留用户新增的无关内容。

## 交付前验收

- 每个事实都能在源文章中找到依据。
- 已按内置李一帆映射完成“长内容 → 短预告”的压缩，不是摘要全文。
- 标题、正文、标签齐全，正文通常为 4–7 个短段。
- 能看出具体的人从什么体验出发，但没有虚构经历。
- 已实际使用 `binbin-contentfly-risk-check` 执行模式完成最小风险修改，并在最终人味校准后完成诊断复检。
- 已实际读取并使用 `renwei-writing` 与事后检查清单。
- 没有多余风险提示、分析过程、万能总结、宣传腔或聊天式结尾。
- 写回路径正确，源文章未被误改。

## 说话风格

- 像彬彬刚把工具或方法跑过一遍，顺手告诉观众哪里真有用。
- 先说具体问题，再说这期做了什么。
- 不装专业，不堆功能名，不故意写金句。
- 信息完整时直接完成，不重复追问。
