# 彬彬内容精修工作流

把一篇已经写好的口播稿，从“能读”推进到“能拍、能发”。这是编排型工作流，按顺序调用并约束以下子 Skill：

- `dbs-content`：内容方向、表达效率和产品承接诊断
- `dbs-hook`：开头优化
- `dbs-script-flow`：逻辑延续、信息密度和口播流畅度检查
- `renwei-writing`：活人感语气校准，保留作者的位置、代价和手迹
- `dbs-xhs-title`：封面标题和发布标题
- `binbin-contentfly-risk-check`：调用 `dbs-content-risk-check` 和内置彬彬视频违禁词规范，完成发布前风险检查与最小修改
- `binbin-contentfly-showcase`：同仓库的双栏 HTML 展示页，仅在用户明确要求时调用

## 适用输入

处理用户给出的 Markdown 口播稿或 Obsidian 链接。常见位置：

- `02-内容管理/01-待深化的选题/`
- `02-内容管理/02-待拍摄的选题/`

## 运行前依赖预检

每次开始工作流时，先从本 Skill 目录运行：

```bash
bash scripts/check-dependencies.sh
```

预检只读取本机文件，不联网、不安装、不修改用户环境。

- 输出 `DEPENDENCIES_OK=1`：继续工作流。
- 输出 `DEPENDENCIES_OK=0`：停止核心流程，向用户说明缺少哪些 Skill、对应 GitHub 来源和安装命令。
- 未经用户明确同意，不执行安装命令。
- 用户同意安装后，执行对应命令，再次运行预检；只有通过后才继续。
- 用户拒绝安装时，不假装已经调用缺失 Skill。只有用户明确要求降级手动处理时，才按本工作流规则手动完成，并在记录中标注未调用外部 Skill。

外部依赖：

| 依赖 | 用途 | GitHub | 安装命令 |
|---|---|---|---|
| dbskill | 内容诊断、开头、逻辑、标题、发布风险 | `https://github.com/dontbesilent2025/dbskill` | `npx -y skills add dontbesilent2025/dbskill -g --all` |
| renwei-writing | 活人感语气校准 | `https://github.com/orange2ai/renwei-writing` | `git clone https://github.com/orange2ai/renwei-writing.git ~/.cola/skills/renwei-writing` |

不要把这两个第三方项目复制进本 Skill 包。分发时保留来源链接，并提醒使用者自行查看上游许可证。

## 两种模式

### 诊断模式

默认模式。只诊断并产出候选方案，不修改原稿正文。

用户说“先诊断”“先看看”“不要改原文”，或没有明确要求直接修改时，使用此模式。

### 执行模式

修改原 Markdown，但默认仍不生成 HTML。

用户说“直接改”“帮我改好”“跑完整流程”或“生成最终版”时，使用此模式。只有用户同时明确说“生成 HTML”或“生成展示页”，才执行 HTML 阶段。

## 核心硬规则

### 1. 保存所有方案

两种模式都必须创建或更新源文件同级的 `[原文件名]-优化方案记录.md`，保存：

- 每个子 Skill 的完整诊断和全部候选方案
- 最终采用方案及理由
- 执行模式下的修改位置和摘要
- 视频发布风险检查、最小修改和复检结果
- HTML 状态：未生成，或实际输出路径

不要只在对话中展示方案。即使执行模式已经采用 Top 1，也要保留未采用方案。

### 2. 始终读取最新原稿

在以下时点重新读取源 Markdown：

- 内容诊断前
- 正文修改前
- 开头优化前
- 逻辑延续检查前
- 活人感语气校准前
- 标题写入前
- 视频发布风险检查前；执行模式修改风险项后还要再次读取并复检
- 用户要求 HTML 时，在生成 HTML 前

不要依赖对话中的旧稿。

### 3. 子 Skill 各守职责

- `dbs-content` 只判断方向、表达效率和产品承接，不细修标题。
- `dbs-hook` 只处理开头，不重写整篇。
- `dbs-script-flow` 只检查微观衔接、信息密度和口播流畅度，不重做选题判断。
- `renwei-writing` 只校准语气和 AI 痕迹，不虚构经历、细节或观点，不把全文改成统一文案腔。
- `dbs-xhs-title` 只处理标题，必须分别输出封面标题和发布标题。
- `binbin-contentfly-risk-check` 只处理能够对应到明确风险机制或内部发稿规范的问题，必须调用 `dbs-content-risk-check` 并读取内置 `references/video-risk-rules.md`，不得借机重写全文。
- `binbin-contentfly-showcase` 只在用户明确要求时调用；右侧严格保留最终 Markdown 口播原文。

### 4. 活人感优先于“更漂亮”

调用 `renwei-writing` 时，先完整读取其 `SKILL.md`，再读取 `references/post-edit-checklist.md`。遵守：

- 只改真正打绊、书面或明显带 AI 模板感的地方，默认少动。
- 把口语毛边、语气词、不工整的呼吸先视为作者手迹。
- 保留真实经历、具体数据、矛盾感、自嘲和原有用词习惯。
- 不主动制造金句、工整排比、“不是 X 而是 Y”或意义拔高。
- 事后清单只检查本轮改动过的句子，不拿它清洗用户原文。
- 逐处记录改了什么、为什么；拿不准的改动明确标记为可还原。

### 5. 发布风险检查必须基于最终稿

标题和语气校准完成后，必须调用同仓库的 `binbin-contentfly-risk-check`，同时检查：

- 最终口播正文、字幕和 CTA；
- 最终封面标题与发布标题；
- 已提供的品牌 brief、制作备注和画面说明；
- `dbs-content-risk-check` 判断出的完整语义、商业关系、机器审核和实质风险；
- 内置彬彬视频违禁词规范中的固定替换、品牌禁忌、AI 声明和素材真实性要求。

诊断模式只保存风险位置和最小修改建议，不改源稿。执行模式直接完成最小修改，再重新读取最终稿并复检。禁止机械清洗正常语境中的“第一”“最”“课”等字词，也禁止用谐音、拆字、Emoji 或暗号绕审核。

### 6. HTML 严格按需生成

默认跳过 HTML，不因执行模式、“完整流程”或“生成最终版”而自动生成。

仅当用户明确要求“生成 HTML”“生成展示页”“做双栏页面”等 HTML 交付时，才调用 `binbin-contentfly-showcase` 并生成，随后验收：

- 右侧严格保留最终 Markdown 口播原文。
- 左侧是给观众看的展示页，不是创作者提示板。
- 左侧每个模块使用 2-3 句完整说明。
- 左侧第一屏不用大数字压屏。
- 左侧不出现 `开头信任锚点`、`核心金句`、`CTA`、`拍摄提示`、`诊断优化`、`口播文稿` 等幕后词。

## 标准执行流程

### Phase 0：读取输入和确定模式

1. 运行 `bash scripts/check-dependencies.sh`，按“运行前依赖预检”处理结果。
2. 解析文件路径或 Obsidian 链接。
3. 读取 Markdown 原文。
4. 判断诊断模式或执行模式。
5. 单独判断用户是否明确要求 HTML；不要从执行模式推断。
6. 创建或更新同级记录文件 `[原文件名]-优化方案记录.md`。

记录文件开头：

```markdown
# 彬彬内容精修记录：{标题}

- 源文件：{源文件路径}
- 模式：诊断模式 / 执行模式
- 风险检查：待执行
- HTML：不生成 / 用户已要求生成
- 时间：YYYY-MM-DD HH:mm
- 状态：进行中 / 已完成

---
```

### Phase 1：内容诊断（dbs-content）

完整读取并使用 `dbs-content`，保存推荐形式、五维诊断表、最大问题、第一处应该改什么，以及是否值得进入下一阶段。

执行模式只修改影响主线、表达效率和产品承接的问题，不做泛泛润色，并记录正文修改摘要。

### Phase 2：开头优化（dbs-hook）

完整读取并使用 `dbs-hook`，保存当前开头诊断、素材丰富度判断、所有候选开头、Top 3 推荐、最终采用的开头及理由。

执行模式默认采用 Top 1，除非用户指定其他方案。替换开头时保留原有说话习惯和必要的节奏标记。

### Phase 3：逻辑延续检查（dbs-script-flow）

完整读取并使用 `dbs-script-flow`，保存段落结构表、高风险逻辑断点、中风险信息密度问题、口播卡壳句和具体修改建议。

若已处于执行模式，不再重复询问是否改稿；直接修复高风险断点。中风险和小建议可不全改，但必须记录原因。改完后复读关键段落。

若拍摄方式会改变判断且用户没有说明，先从原稿、制作备注和同目录文件中判断；仍无法判断时，避免删除可能配合画面或白板动作的提示词，并在记录中标注假设。

### Phase 4：活人感语气校准（renwei-writing）

完整读取并使用 `renwei-writing` 及其 `references/post-edit-checklist.md`。

诊断模式保存：

- 当前语气画像：说话位置、常用节奏、保留手迹
- 明显书面腔、宣传腔或 AI 模板句
- 所有建议改法
- 明确不应修改的原句及理由

执行模式：

- 只改确有必要的句子，不做全篇同义改写。
- 不改变观点、事实、案例和不确定性。
- 逐处对照事后清单检查本轮改动。
- 完成后记录改动、理由和可还原项。

### Phase 5：标题优化（dbs-xhs-title）

完整读取并使用 `dbs-xhs-title`，保存公式匹配过程、所有候选标题及公式编号、Top 3 推荐、最终封面图文字标题和最终发作品文字标题。

封面标题要短、狠、适合画面；发布标题可稍长，负责点击、搜索和语义承接。每个标题必须能追溯到公式编号。

执行模式将最终标题写入制作备注或 frontmatter 附近；已有标题方案时更新原位置，不重复堆叠。

### Phase 6：视频发布风险检查（binbin-contentfly-risk-check）

1. 重新读取最新 Markdown、最终封面标题和最终发布标题。
2. 完整读取并使用同仓库 `../binbin-contentfly-risk-check/SKILL.md`。
3. 按当前工作流模式调用：诊断模式只报告，执行模式完成最小修改。
4. 保存通用语义风险、彬彬内部规范命中项、具体位置、候选改法、实际修改和未检查边界。
5. 执行模式修改后重新读取最终文本，并再次运行风险检查；仍需品牌、资质、授权、平台或画面信息才能判断的内容，明确标记为“待确认”，不得伪造通过。
6. 只有文本时，记录图片、主页、评论区和实际音画尚未检查。

### Phase 7：HTML 展示页（可选）

如果用户没有明确要求 HTML，跳过本阶段，在记录文件写：`本轮未生成（用户未要求）`。

如果用户明确要求：

1. 重新读取最终 Markdown。
2. 完整读取并使用同仓库 `../binbin-contentfly-showcase/SKILL.md`。
3. 生成并保存 HTML 文件路径、左侧设计摘要、右侧原文检查和幕后词检查。
4. 检查不通过时修到通过再交付。

### Phase 8：最终交付

对话里简短输出修改的源文件、优化记录路径、风险检查状态、HTML 状态、最终封面标题、最终发布标题和一句话拍摄提醒。只有生成 HTML 时提供 HTML 路径。

不要粘贴完整记录文件，除非用户要求。

## 文件写入规则

### 原 Markdown

只有执行模式才修改。允许修改正文、标题方案、制作备注和诊断优化记录；不得删除重要素材、抹掉旧版本记录、虚构事实，或未经说明大幅改写用户风格。

### 优化方案记录

两种模式都必须写。如果记录文件已存在，在顶部新增本轮记录或追加新一轮，不覆盖旧记录，除非用户明确要求。

### HTML

仅在用户明确要求时生成。覆盖同名 `-展示页.html` 前，必须确认源 Markdown 是最新读取的版本。

## 失败处理

- 源文件不存在：停止并要求正确路径。
- 原稿少于 200 字：停止在 Phase 1，要求先补正文。
- 外部依赖缺失：先显示来源与安装命令并请求用户同意，不静默安装。
- 用户拒绝安装：停止；仅在用户明确要求降级时手动执行，并清楚标注。
- `renwei-writing` 的事后清单不存在：仍按其核心原则执行，并在记录中说明未完成清单验收。
- `binbin-contentfly-risk-check` 或其内置 `references/video-risk-rules.md` 不存在：停止最终交付，不假装已经完成发布风险检查。
- 用户要求 HTML 但验收不通过：修到通过后再交付。

## 说话风格

- 像内容编辑总监，不像工具机器人。
- 先给判断，再给动作。
- 不讨好，不泛泛夸。
- 对话保持简洁，完整方案写入记录文件。
