# 彬彬视频发布风险检查

把通用语义风险判断和彬彬账号内部发稿规范合并为一次发布前检查。不要把词表命中直接写成平台违规，也不要为了降低风险把作者的强观点、口语和传播钩子改平。

## 运行前依赖预检

从本 Skill 目录运行：

```bash
bash scripts/check-dependencies.sh
```

- 输出 `RISK_CHECK_DEPENDENCIES_OK=1`：记录 `DBS_CONTENT_RISK_CHECK_PATH`，继续。
- 输出 `RISK_CHECK_DEPENDENCIES_OK=0`：停止核心流程，说明缺少 `dbs-content-risk-check` 及其 GitHub 来源；未经用户同意不得安装。
- 用户明确允许降级手动检查时，可以只使用内置规范，但必须标注“未实际调用 dbs-content-risk-check，未完成完整语义风险检查”。

外部依赖由 `https://github.com/dontbesilent2025/dbskill` 提供。取得用户同意后才可执行：

```bash
npx -y skills add dontbesilent2025/dbskill -g --all
```

## 必读资料

每次运行都必须完整读取：

1. 预检找到的 `dbs-content-risk-check/SKILL.md`；
2. 本 Skill 的 `references/video-risk-rules.md`。

前者负责完整语义、商业关系、机器审核、视觉和声音等通用风险；后者是彬彬账号的内部发稿规范与经验词表。第三方 Skill 不复制进本仓库。

## 两种模式

### 诊断模式

用户说“检查一下”“先看看”“排雷”或没有明确要求修改时使用。定位具体问题、说明风险机制并提供局部替换方案，不修改源文件。

### 执行模式

用户说“直接改”“去掉违禁词”“改成能发布的版本”，或者由 `binbin-contentfly-polish-pipeline` 的执行模式调用时使用。只做降低明确风险所需的最小改动，不重写全文。

## 检查范围

根据用户实际提供的材料检查：

- 封面标题和画面文字；
- 发布标题、正文和话题标签；
- 口播、字幕、制作备注和 CTA；
- 品牌 brief、利益关系和指定替换规则；
- 图片、视频、屏幕录制和声音中可见或可听的信息。

只有文本时照常完成文本检查，并说明图片、主页、评论区和实际音画尚未纳入判断。不要因为缺少某一类材料而放弃全部检查。

## 标准流程

1. 识别目标平台、内容位置、内容目的、是否商单和已有 brief。
2. 重新读取待发布的最新文本；不要检查对话中的旧版本。
3. 调用 `dbs-content-risk-check`，分别判断平台机器可能识别什么、内容本身有什么实质风险。
4. 使用 `references/video-risk-rules.md` 逐项检查内部禁用表达、品牌禁忌、AI 内容声明、对比素材、重复内容和账号操作风险。
5. 合并结果并去重：同一句只保留最具体的风险机制和最小修改动作。
6. 诊断模式保存问题与候选改法；执行模式执行局部修改。
7. 执行模式修改后重新读取最终文本，并再次完成通用语义检查和内部规范检查。
8. 输出已处理项、仍需用户确认项和未检查边界。

## 判断优先级

发生冲突时按以下顺序处理：

1. 已核验的当前官方平台规则和安全边界；
2. 当前项目或品牌 brief 的明确要求，但不得用它绕过安全和官方规则；
3. `references/video-risk-rules.md` 中的彬彬账号内部规范；
4. 无法核验的经验判断，只能写成风险提示，不能写成确定结论。

内置规范不是所有平台的官方违禁词表。需要特别处理以下情况：

- “最”“第一”“王”等词先判断是排名或权威宣传，还是顺序、型号、个人偏好和正常叙事；“第一个步骤”不能机械删除。
- “课”“课堂”等教育词必须结合招生、培训、升学和效果承诺判断，不把普通课程讨论自动写成实质违规。
- 品牌专项要求只用于对应品牌，不扩展成所有内容的通用禁令。
- 截图经验和未核验规则写成账号内部保守规范或待确认项，不声称“出现必限流”。
- 用户或 brief 要求使用谐音、拆字或 Emoji 变体时，不主动把这种做法推广成通用绕审策略；记录其来源，并继续检查完整语义是否存在风险。

## 最小修改规则

- 修改必须对应一个说得清的风险机制或明确的内部发稿规则。
- 能换一个词解决时不重写整句，能改一句解决时不重写整段。
- 保留真实数据、真实经历、强观点、情绪张力、口语毛边和有效 Hook。
- 不虚构资质、授权、证据、效果、活动期限和商业关系。
- 不生成谐音、拆字、暗号、隐藏联系方式或其他绕审核方案。
- 不写“保证能发”“100% 合规”“一定不限流”。
- 三行贴片只按 `dbs-content-risk-check` 的触发条件生成，不能代替正文修改、报备或官方发布入口。

## 默认输出

```markdown
## 先说结论
- 通用语义风险：...
- 彬彬内部规范：...

## 建议优先处理
### 1. 「精确引用」
- 风险机制/内部规则：...
- 最小修改：...

## 可能触发机器审核
...

## 发布前确认
- ...

## 检查边界
- ...
```

执行模式额外输出：

```markdown
## 已执行修改
| 位置 | 原文 | 修改后 | 原因 |
|---|---|---|---|

## 复检结果
- 通用语义检查：通过 / 仍有待确认项
- 彬彬内部规范：通过 / 仍有待确认项
```

没有发现需要处理的问题时，明确写：

> 基于已提供的材料，没有发现需要优先修改的发布风险；彬彬内部规范检查也未发现明确命中项。

## 写回规则

- 独立调用时，只有执行模式才修改源文件。
- 诊断结果默认写入对话；用户指定记录文件时才落盘。
- 由精修工作流调用时，把完整检查、修改记录和复检结果写入其 `[原文件名]-优化方案记录.md`，不另建重复记录。
- 修改文件前重新读取最新版本，避免覆盖用户新增内容。

## 失败处理

- `dbs-content-risk-check` 缺失：停止并请求安装许可；用户允许降级时才继续。
- 内置 reference 缺失：停止，不假装完成彬彬内部规范检查。
- 平台或商业属性会改变结论：先完成能完成的部分，最多追问一个真正影响判断的问题。
- 结论依赖当前平台政策：只查询官方规则，并注明适用对象、更新时间和链接。
